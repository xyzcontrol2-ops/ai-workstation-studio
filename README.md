# AYRA Command Center

AYRA is a TanStack Start dashboard with a LangGraph-backed mission planner and a PostgreSQL-backed workforce registry. The mission API persists structured task drafts with department suggestions, prerequisites, and verification criteria. A separately started `npm run worker` process can execute explicitly assigned, eligible tasks through the configured per-agent model gateway only when the persisted owner policy is unpaused, grants reversible-task permission, and has sufficient verified performance evidence; absent policy defaults to paused. Pausing stops future claims, not an already-running provider call. Successful output is persisted with the task left in `VERIFYING`; execution is not independent quality verification. Creating an agent profile does not start a process, and planned catalog profiles cannot execute.

The additive future-proof contracts, model gateway, evidence-based phase audit, and unresolved compatibility decisions are documented in [the architecture foundation](./docs/future-proof-architecture-foundation.md). The gateway currently wraps one OpenAI-compatible adapter. The task worker is connected to the database and configured model gateway; tenant, event-store, memory, and plugin contracts do not imply connected runtime implementations.

## Requirements

- Node.js 22 or newer
- PostgreSQL for workforce persistence
- An OpenAI-compatible model endpoint and model API key (for example, a provider API or a self-hosted LiteLLM gateway)
- A random AYRA API token of at least 32 characters
- A separate random AYRA owner token of at least 32 characters for plan approval decisions
- A private 32-byte `AYRA_CREDENTIAL_VAULT_KEY` before storing provider credentials; keep it stable because changing it makes stored credentials unreadable

## Run locally

1. Copy `.env.example` to `.env`.
2. Set `AYRA_API_TOKEN`, `AYRA_OWNER_TOKEN`, and `DATABASE_URL` for a dedicated local PostgreSQL database. Configure `AYRA_CREDENTIAL_VAULT_KEY` with 32 cryptographically random bytes (hex or base64) before storing provider credentials, and keep a protected recovery copy. Set `AYRA_MODEL_NAME`, `AYRA_MODEL_API_KEY`, and optionally `AYRA_MODEL_BASE_URL` for model-backed mission planning.
3. Install packages, validate the schema, and generate the Prisma client:

   ```powershell
   npm install
   npm run db:validate
   npm run db:generate
   ```

4. Review the SQL files under `prisma/migrations`. The initial migration is a baseline; later migrations add schema changes. Apply them only to a verified database whose migration history is understood; do not apply the baseline to a database with existing untracked tables. Then migrate and install the department definitions:

   ```powershell
   npm run db:migrate
   npm run db:seed:departments
   ```

5. Start the backend and frontend in separate terminals, in this order. Wait for the backend to report that it is ready on port 4040 before starting the frontend on port 3030. Both commands use strict ports and stop rather than switch ports. Start them sequentially because both development servers use the generated TanStack route tree:

   ```powershell
   npm run dev:backend
   ```

   ```powershell
   npm run dev
   ```

6. Open the UI-only frontend at `http://localhost:3030`. Port 3030 rejects `/api/*`; port 4040 is API-only and its root/UI routes return 404. Browser API requests go directly to `http://localhost:4040`; the AYRA API token is held in tab memory and is not saved in browser storage.

For a production build, run `npm run build`, then start the backend with `npm start` and the frontend preview with `npm run preview` in separate terminals. Keep the backend on port 4040 and frontend on port 3030.

If either port is unavailable, inspect its listener before taking action:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 3030,4040 | Select-Object LocalPort,OwningProcess
```

Check and production build:

```powershell
npm run check
npm run build
```

The live worker smoke test is skipped by default. To opt in, set `AYRA_E2E_ENABLE=1`, `AYRA_E2E_AGENT_ID` to an existing `AVAILABLE` catalog agent with a non-planned profile and configured model assignment, and point `DATABASE_URL` at a dedicated test database before running `npm test`. The persisted workforce autonomy policy must be unpaused at L2 or above, grant `EXECUTE_REVERSIBLE_TASKS`, and have sufficient recorded performance evidence. This test makes a real provider call and may incur provider charges. When enabled, missing prerequisites or unsuccessful execution fail the test; it creates and removes its own mission and task and targets only that task.

Reserve failover is a separate approved workflow: an owner must approve a persisted reserve plan in the Workforce Command Center. On a failed task execution, the worker may transfer it only when the persisted policy is unpaused and effectively L3 or higher, grants `EXECUTE_APPROVED_WORKFLOWS`, meets performance thresholds, and permits another retry. The worker rechecks policy, mission/dependency state, reserve membership, and current agent readiness in a serializable transaction; task output and execution history remain intact. Manual transfer remains owner-authorized. This workflow has focused unit coverage but has not been exercised against a live database or provider in this environment.

## Owner authentication setup

- Open the AYRA frontend at `http://localhost:3030/`. The API-only backend listens on `http://localhost:4040`; do not use it as a frontend URL.
- Open `http://localhost:3030/owner-auth` on the AYRA frontend.
- First-time setup generates a 256-bit random owner token, stores it only in the server-side `.env` protected secret file, and shows it once for the owner to copy into a password manager.
- The browser login creates an HttpOnly, `SameSite=Strict` owner session. AYRA does not store the owner token in `localStorage`, frontend source, or chat logs.
- The setup and rotation screens are restricted to loopback/local-host requests.
- Owner rotation requires an active owner session and generates a replacement token once. The old token is invalidated after `.env` is updated and server sessions are revoked.
- If the token is lost, stop AYRA, preserve or remove the old server `.env` owner-token line safely, restart on localhost, and use the setup screen to generate a replacement. Revoke or clean up any password-manager copy of the lost token.

The owner emergency-stop route now persists a paused `WorkforceAutonomyPolicy` and audit/version record when PostgreSQL is configured. The worker rechecks that persisted pause before claims and provider/tool execution and leaves a paused task assignable rather than failed or sent to reserve failover. The database-independent process stop remains fail-closed for mission creation; stopping does not claim to cancel a provider call already in progress. Live database, cross-process, and in-flight cancellation verification remains required.

The mission API requires bearer-token authorization, accepts bounded JSON requests, validates the objective, and returns a structured plan. Model credentials and the API token stay server-side. Do not expose the development server directly to the internet.

## Hybrid provider and model control

- The Models dashboard persists system-wide AUTO, MANUAL, HYBRID, and AI_ASSISTED settings in `SystemModelControl`; per-agent model assignments retain their own mode, pin, pause, policy, and fallback-credential selections. Global control and automation-policy writes require the distinct owner token.
- Mission planning, PRD generation, architecture generation, and worker task execution use the shared controlled gateway. AUTO/HYBRID candidate selection requires a connected provider, available model, and a tested credential owned by the configured user or authorized owner (except supported local providers that need no credential); it can prefer configured provider order and uses observed successful-route and latency evidence when available. The worker only claims tasks assigned to non-archived agents in `AVAILABLE` or `ASSIGNED` lifecycle states, with completed dependencies and no pending mission approval; it rechecks these conditions atomically when claiming. Eligible tasks are ordered by persisted mission priority, earliest task deadline, task priority, and stable creation/id order. Successful output is persisted as `VERIFYING`, not as verified completion.
- Classified transient provider failures retry within the configured limit. AUTO/HYBRID can use only an explicitly configured, policy-allowed fallback; MANUAL never switches providers, AI_ASSISTED records a recommendation without switching, and paused or policy-blocked calls stop. Route outcomes and safe failure categories are persisted to routing history and audit logs. Provider/model state is re-evaluated, and rate-limited/transiently failed providers may be probed for recovery after a cooldown.
- Provider price and independent quality evidence are not currently available. Any configured spend ceiling or quality threshold therefore fails closed instead of estimating or inventing a value; cost is recorded as unavailable. Latency thresholds also require observed evidence.
- The Models dashboard’s “Why this decision?” disclosure reads persisted routing-decision evidence. Automatic selection stores the eligible-candidate count, ranking criteria, and up to 10 ranked provider/model routes with observed attempt, success-rate, and latency data; credential identities are excluded. Configured primary/fallback routes are distinguished from ranked candidates. Routes beyond the stored top 10 and expected outcomes are not persisted and are explicitly identified as unavailable.
- The runtime adapter currently supports OpenAI-compatible endpoints and selected local OpenAI-compatible servers. Anthropic, Gemini, Azure OpenAI, Bedrock, Vertex, and Hugging Face require dedicated execution adapters and are not represented as working model-call integrations.
- If no persisted system-control row exists, the legacy `AYRA_MODEL_NAME` / `AYRA_MODEL_API_KEY` environment route remains available in HYBRID mode, but has no registry identity or configured fallback. Persisted routing requires applying the additive migrations, including `20261124090000_routing_candidate_evidence`, and configuring tested provider/model/credential records in the dashboard.
- This implementation has not been verified against a live database or provider in this environment. A passing local unit test or build is not production routing evidence.

## Workforce registry (Phase 03 foundation)

- `/agents` provides a searchable, paginated PostgreSQL-backed agent directory and profile registration, editing, suspension, and soft archive. Profile versions, agent events, and audit records are written in the same transactions as profile changes.
- `/departments` provides a PostgreSQL-backed department directory, department create/update, and director assignment. Database uniqueness constraints protect case/Unicode-normalized department names, department codes, and the one-director-per-department/agent relationship. Agent department moves are validated against director and active-work relationships; archiving is blocked while an agent directs a department, has active direct reports, or has an active assignment. `npm run db:seed:departments` synchronizes the 20 department definitions from the Phase 03 brief; it does not create agent records or fabricate activity/KPIs.
- `GET /api/agents` and `GET /api/departments` support bounded pagination and search. Agent create, update, and archive and department create/update APIs require the AYRA bearer token, validate inputs, and persist audit events.
- Profiles start as `REGISTERED`. Editing cannot set an agent to `AVAILABLE` or `EXECUTING`; the scheduler and capability-readiness workflows control lifecycle transitions. The worker rechecks that an assigned agent is not archived and is `AVAILABLE` or `ASSIGNED` when claiming a task.
- The command-center overview reads workforce totals and mission/task counts from PostgreSQL when configured and shows unavailable metrics as `—` when it cannot connect. Worker executions and task outputs are persisted when the worker is configured and run.
- Workforce APIs and migration have not been verified against a live database on this host: PostgreSQL/`psql` and `DATABASE_URL` are absent. The generated migration is unapplied. Use a fresh, disposable local database and review the SQL before applying it.
- `POST /api/organization-proposals` plans an objective, compares its department and required-skill needs with real registered departments and agent profiles, and saves an owner-review proposal. It only recommends candidate profiles; it does not create departments, teams, assignments, reporting changes, or agents. `GET /api/organization-proposals` lists the latest 50 proposals. Both endpoints require the configured AYRA bearer token; proposal creation also requires PostgreSQL and model configuration.
- Mission tasks now include `requiredSkills`; candidate matching uses exact normalized skill names/categories and only considers `AVAILABLE` agents without active assignments. Missing skills, unspecified skills, or missing/disabled departments are reported rather than filled with fabricated agents. There is not yet an authenticated approval/acceptance endpoint or any automatic organization change.
- Workforce evolution can create an owner-authorized specialist-role recommendation from capability gaps recurring in completed/failed mission tasks and absent from every currently assignment-eligible agent. The recommendation is saved to the existing `ImprovementProposal` registry with a source evidence hash. It does not create agents or credentials, research providers/tools, or perform shadow tests; those remain unavailable.

## Global Agent Library and role catalog

- `/agent-library` presents a version-controlled blueprint of exactly 50 software-factory modules and 300 sequential role profiles, with module dependencies, role inputs/outputs, handoffs, verification criteria, proposed public repositories, and known custom-work gaps.
- These 300 entries are blueprints, not registered `Agent` records or executable workers. The page labels repository links as recommendations and keeps the existing PostgreSQL-backed repository discovery/import governance separate.
- The generated report includes dated primary-source profiles for all 31 catalog repositories, module/role mappings, install guidance, release/license indicators, limitations and explicit source-audit boundaries. Profile scope varies by repository; no entry implies source audit, adoption approval or operational integration. AutoGen is marked archived, legacy SWE-agent points to its maintainers' mini-SWE-agent successor, dbt uses its canonical repository URL, and Presidio uses its canonical repository URL.
- The report also documents architecture and operational verification boundaries; no third-party code was installed or executed. Regenerate it with `npm run catalog:report`.

## Software factory (Phase 04 foundation)

- `/software-factory` provides authenticated software-idea intake and a project directory. It only displays project totals and lifecycle counts returned from PostgreSQL; unavailable database data remains unavailable rather than being replaced with demo metrics.
- `POST /api/software-projects` stores the supplied project name and idea as `IDEA`, and writes a matching project event and audit record in one transaction. `GET /api/software-projects` returns persisted projects, recent events, and database-grouped status counts; it supports a status filter and returns at most 100 records.
- `GET/POST /api/software-projects/:id/requirements` lists and records structured draft requirements with server-assigned per-project IDs (`REQ-001`, `REQ-002`, …), a requirement type, and explicit acceptance criteria. The transaction also adds a project event and audit record. Duplicate numbering under concurrent creation is protected by serializable transactions and unique constraints.
- `GET/POST /api/software-projects/:id/requirements/:requirementId/evidence` lists or records immutable requirement evidence. Supported types are code, test, build, documentation, deployment, and other evidence; results are observed/passed/failed. Optional task links are accepted only when the task belongs to the project and is already linked to the requirement. Evidence stores a SHA-256 content hash and capture timestamp but never changes the requirement to `IMPLEMENTED` or `VERIFIED` by itself.
- `POST /api/software-projects/:id/requirements/:requirementId/status` uses the separate owner token to mark a requirement `IMPLEMENTED` or `VERIFIED` from explicit evidence IDs. Implementation requires approved status; verification requires approved or implemented status plus at least one passing test or build evidence record. Failed evidence is rejected. This is owner-attested evidence status, not proof of an independent worker or production run.
- `GET/POST /api/software-projects/:id/adrs` lists or creates versioned architecture decision records with context, alternatives, trade-offs, consequences, dependencies, and content hashes. `POST /api/software-projects/:id/adrs/:adrId/decision` uses the separate owner token to approve or reject an ADR; approval supersedes earlier approved ADRs transactionally.
- `GET/POST /api/software-projects/:id/requirement-interviews` lists or creates deterministic versioned requirement interviews from the stored project idea. `POST /api/software-projects/:id/requirement-interviews/:interviewId/answers` persists answers and clarification-task progress; `POST /api/software-projects/:id/requirement-interviews/:interviewId/decision` uses the owner token to approve/reject an answered interview and supersedes prior approvals.
- `GET/POST /api/software-projects/:id/scope` lists or creates MVP/V1/future scope releases. Draft creation validates requirement IDs against approved requirements, detects unapproved scope additions, and stores feature/API/database/test mappings. `POST /api/software-projects/:id/scope/:scopeId/decision` uses the owner token to approve/reject and supersede scope for the same release type.
- `GET/POST /api/software-projects/:id/dependencies` lists or captures immutable dependency snapshots from the project's `AYRA_PROJECT_WORKSPACES_ROOT/<project-id>` workspace (`package.json`, `package-lock.json`, and source evidence). The snapshot records direct/transitive package edges, package-name cycles, resolved-version conflicts, direct major-version changes, and unused-package candidates. `POST /api/software-projects/:id/dependencies/:snapshotId/decision` uses the owner token to approve/reject and supersede snapshots.
- `GET/POST /api/software-projects/:id/genome` lists or captures a machine-readable software genome from the project's configured workspace (package manifest, Prisma schema, source modules, route inventory, and deployment indicators). The snapshot stores framework, architecture, dependencies, database models, API route inventory, deployment evidence, and provenance hashes. `POST /api/software-projects/:id/genome/:genomeId/decision` uses the owner token to approve/reject and supersede genomes.
- `GET/POST /api/software-projects/:id/codebase-index` lists or captures a bounded static codebase index. Capture requires the owner-configured `AYRA_PROJECT_WORKSPACES_ROOT`, with each project's source under `<root>/<project-id>/src`; AYRA does not provision this root, and capture returns `503` until the root and project source directory are configured. It never scans the AYRA server's working directory. Route/service/component entry points, imports, naming/import conventions, normalized duplicate candidates, and same-export reuse candidates are indexed. Paths are confined to the configured per-project directory and symlinked source entries are not followed. `POST /api/software-projects/:id/codebase-index/:indexId/decision` uses the owner token to approve/reject and supersede the index. Candidates are not asserted as verified duplicates or reusable implementation.
- `GET/POST /api/software-projects/:id/workspace-policies` lists or creates versioned development/testing/staging/production workspace policies. Policies record CPU/RAM/disk/time limits and filesystem/network boundaries and execute only an exact Docker/Podman/NONE availability probe. `POST /api/software-projects/:id/workspace-policies/:policyId/decision` uses the owner token to approve/reject and supersede policies; production approval is blocked unless the runtime probe reports AVAILABLE. The probe is not container creation or isolation verification.
- `GET/POST /api/software-projects/:id/development-assignments` lists or creates project-task development assignments with a workspace name, branch name, project-relative file paths, migration paths, and merge dependencies. The service detects file, migration, and declared merge-dependency overlaps and refuses duplicate workspace, branch, or task assignments. `POST /api/software-projects/:id/development-assignments/:assignmentId/decision` uses the owner token to approve/reject it; approval is blocked while detected conflicts remain. It does not execute Git, create worktrees, or merge code.
- `GET/POST /api/software-projects/:id/checkpoints` lists or captures development checkpoint metadata with optional task ID, code/schema/config/test hashes, and bounded artifact references. `POST /api/software-projects/:id/checkpoints/:checkpointId/decision` lets the owner approve/reject a checkpoint, request restore, or verify restore with independent evidence. Saving or approving a checkpoint does not restore code, schema, config, or test state; restore verification is never inferred from the request alone.
- `GET/POST /api/software-projects/$id/missions/$missionId/continuity` lists or creates durable mission continuity runs. CREATE persists ordered steps and an idempotency key; ADVANCE, INTERRUPT, RESUME, FAIL, and COMPLETE update persisted state and skip repeated operation keys. This is continuity-state persistence, not a real worker or verified restart recovery.
- `GET/POST /api/software-projects/:id/digital-twin` lists or captures immutable Cognitive Digital Twin snapshots. The latest approved architecture proposal is included with its components, dependencies, data/API design, security controls, integrations, and deployment assumptions. Database evidence includes entities and requirement links from the latest approved PRD plus persisted schema-hash checkpoints; structured relationships are included only when present and requirement-validated in the approved PRD. Infrastructure and performance remain explicitly unavailable until measured telemetry exists.
- `GET/POST /api/software-projects/:id/simulations` lists or registers versioned Software Future Simulator experiments. Scenarios support bounded concurrent-user, duration, ramp (no longer than the run), operation, traffic, database, provider, network, resource, deployment, agent, and synchronization-conflict configuration. Registered experiments remain NOT_RUN with empty measured results and no fabricated bottlenecks or recommendations.
- `GET/POST /api/software-projects/:id/technology-sandbox` lists or registers versioned proposals for evaluating frameworks, databases, AI agents, automation, architectures, and deployment approaches. Proposals include a hypothesis, evaluation plan, comparison targets, and compatibility checks. The owner decision endpoint records approval/rejection; execution remains `NOT_RUN`, isolation `NOT_PROVISIONED`, and compatibility `NOT_REVIEWED` until a real isolated evaluator is connected.
- `GET/POST /api/software-projects/:id/improvement-assessments` lists or captures versioned recommendations from the latest persisted dependency snapshot and/or static codebase index. Each assessment records the source snapshot IDs, versions, content hashes, recommendation evidence, and an assessment hash. Findings remain review candidates; no patch is generated, no tests or benchmarks run, and no production changes are made.
- `GET/POST /api/software-projects/:id/engineering-swarms` lists or captures team proposals for owner-approved project missions in `PLANNING`. Candidate matches use registered department, agent lifecycle, active assignment, and exact skill/category records; missing coverage remains a staffing gap. The owner token can approve or reject a proposal at `/api/software-projects/:id/engineering-swarms/:proposalId/decision`; this review creates no `AgentAssignment`, launches no worker, and claims no consensus or peer review.
- `GET/POST /api/software-product-lab` lists or creates separate Product Lab experiment records. Creation stores a separate `SoftwareProject` at `IDEA`, a DRAFT experiment, hypothesis, normalized source-evidence hash, and transactional project/audit events. This separates records only; it does not provision an isolated runtime or filesystem. `/api/software-product-lab/:experimentId/decision` uses the owner token to approve or reject the proposal; approval is review-only and starts no market validation, prototype, engineering, test, or release workflow.
- `GET/POST /api/software-projects/:id/recovery-assessments` lists or captures versioned recovery assessments only from persisted failed missions/tasks, failed/interrupted continuity runs, or failed test/build/deployment evidence. Reports link source hashes and eligible approved checkpoint candidates; recommendations are owner-review-only. `/api/software-projects/:id/recovery-assessments/:assessmentId/decision` records owner approval/rejection but never retries work, restores a checkpoint, or rolls back a deployment.
- `POST /api/software-projects/:id/technology-sandbox/:experimentId/decision` uses the owner token to approve or reject a proposal for further review; approval does not provision an environment, validate compatibility, run a benchmark, or introduce the technology into production.
- `GET /api/software-projects/:id/engineering-progress` summarizes persisted project, requirement, PRD, architecture, mission/task, and submitted code/test/build/deployment evidence. The response includes source hashes and preserves raw record statuses; it does not claim that a plan was executed or that deployment/release was independently verified.
- PRD, architecture, and project mission planning store provider-reported input/output token counts in the existing execution-cost ledger as soon as valid usage metadata returns, even if later output validation or persistence fails. The project economy endpoint reports those recorded calls. Dollar cost remains unset because provider pricing is not configured; absent usage is not estimated.
- `GET /api/software-projects/:id/engineering-economy` and the project panel summarize the persisted PRD-generation usage ledger by model. They explicitly scope coverage to PRD calls, report unpriced totals as unavailable, and do not infer budgets or non-PRD resource costs.
- `GET/POST /api/software-projects/:id/governance-assessments` lists or captures immutable, source-hashed readiness reviews. The Factory panel distinguishes approved requirements/specifications from submitted test/deployment evidence and unavailable independent inspection, test execution, security, database, performance, and independent-review checks. The owner-token decision endpoint records acknowledge/reject decisions and audit events without changing readiness or authorizing release; the shared token does not identify a person.
- `GET /api/software-projects/:id/knowledge-graph` returns project-scoped nodes and edges for persisted requirements, specifications, features/modules, missions/tasks, explicit dependencies, assignments, evidence, and architecture decisions, plus static API route/method and Prisma model/relationship evidence from the configured project workspace. API files and schema nodes carry source hashes; missing workspaces, routes, or schema files are marked unavailable rather than implied. These are source observations, not proof of deployed endpoints or database state. The Factory page renders this state as a selectable 2D SVG graph. It omits cross-project references and is not tenant-safe cross-project search because the application still uses shared-token authorization without tenant identity.
- `POST /api/software-projects/:id/requirements/:requirementId/approve` uses the separate `AYRA_OWNER_TOKEN` to approve one draft requirement, with project-event and audit records in the same transaction.
- `GET/POST /api/software-projects/:id/prd` loads versioned PRDs or drafts one using only 1–20 approved requirements and the existing 12,000-character planning-input bound. `POST` optionally accepts up to 20 unique `repositoryAssessmentIds` belonging to the same project and attaches those immutable snapshots to that PRD version in the same transaction. The model still receives approved requirements only; attached repository metadata is separate provenance, not a basis for generated claims. Each draft stores content and requirement-source hashes, plus project-event and audit records atomically. The model output is schema-checked against the exact approved requirement IDs; normalized, version-scoped feature/module records and FK-backed requirement, feature/module, and dependency links are persisted in the same transaction. Feature-to-module links are stored only when explicitly supplied; no relationship is inferred from overlapping requirement IDs. Assumptions remain explicitly unverified.
- `POST /api/software-projects/:id/prd/:specificationId/decision` uses `AYRA_OWNER_TOKEN` to approve or reject one specific draft PRD version; rejection requires a reason. Approval supersedes any previously approved PRD version in the same transaction. The content snapshot remains immutable, and approval does not mark implementation or verification complete.
- `GET/POST /api/software-projects/:id/architecture` lists architecture versions or drafts a proposal from exactly one approved PRD and its approved requirements. It validates requirement references and acyclic component dependencies, stores requirement-source/content hashes, and atomically records project/audit events. Third-party integrations and deployment details remain explicitly unverified.
- `POST /api/software-projects/:id/architecture/:specificationId/decision` uses the owner token to approve or reject a specific draft architecture version; the shared specification decision service supersedes a prior approved version atomically. Approval is a review decision only and does not create resources, start implementation, or verify the design.
- `GET/POST /api/software-projects/:id/repository-assessments` lists or captures immutable public GitHub repository metadata using only the official GitHub API and validated owner/repository slugs. Snapshots retain source URLs, retrieval times, metadata hash, license declaration, latest commit/release where available, and visible advisory references. Advisory access can be unavailable or paginated; a snapshot is not a license/legal review, compatibility check, security clearance, or approval to install.
- `GET/POST /api/software-projects/:id/plans` loads persisted planning missions or asks the configured planner for a draft mission outline based only on approved requirements. It requires 1–20 approved requirements and a combined planning input within 12,000 characters; each planned task must reference one or more of those approved IDs. FK-backed task-to-requirement links are persisted on the existing `Task` records with their project `Mission`, dependencies, and any policy hold `Approval`. A project event and audit record are written atomically. `POST /api/software-projects/:id/plans/:missionId/decision` uses the separate `AYRA_OWNER_TOKEN` to approve or reject a held draft; rejection requires a reason. Approval changes only the draft mission state—it does not assign agents or execute tasks, and it does not advance the project lifecycle status.
- The owner token is a separate shared credential, not an individual user identity. Audit `actorId` remains unset until authenticated owner accounts and sessions exist; do not treat bearer-token approval as attributable personal identity.
- Tasks retain their suggested department label, required skills, verification criteria, and prerequisite links. A `departmentId` is set only when the suggestion matches an enabled registered department; a label alone is not evidence of staffing.

Repository research is limited to the public GitHub metadata snapshot above; market research, compatibility testing, task execution, code editing, tests, builds, releases, deployment, and maintenance are not connected. Project lifecycle status remains unchanged until a real stage workflow is recorded.
- Project APIs require the configured AYRA bearer token and PostgreSQL; plan, PRD, and architecture drafting also require the model configuration. Owner decisions use the separate owner token. Do not enter credentials into project descriptions; the server rejects common secret-like values.

## Current mission scope

- Mission planning returns 1–12 structured tasks, with registered department names, explicit required skills, dependency IDs, and verification criteria. The server validates unique task IDs, dependency references, cycles, and approval requirements before saving a plan.
- Mission registration stores a timestamped, plan-hash-bound capability preflight in the existing mission evidence and audit record. It compares each task's explicit skills with persisted agent readiness, permission eligibility, and current assignment capacity; missing requirements and unassessed tasks are shown rather than assigned invented readiness. This is a point-in-time planning snapshot, not an assignment, provider test, execution, or guarantee that later conditions remain unchanged. Existing missions without a valid snapshot return `feasibility: null`.
- A conservative deterministic policy scans the objective and all generated plan text for destructive operations, production changes/deployments, financial actions, sensitive-data disclosure, security/privilege changes, or external communications. High-risk findings create a hold, not an approval workflow or authorization to execute; the pattern checks are not a semantic safety guarantee.
- Mission requests containing common credential-like values are rejected, and similarly detected generated output is discarded before registration. This is defense-in-depth, not a general-purpose DLP system; never submit secrets in mission text.
- Explicit attempts to override AYRA's system/developer instructions are rejected before model invocation. This narrow pattern check is not a comprehensive prompt-injection defense, especially for instructions embedded in future documents or tool responses.
- Task dependency graphs are converted into topological waves showing which tasks could be parallelized. This is a schedule preview; it does not itself assign or execute tasks.
- `POST /api/missions` creates a persisted plan; authenticated `GET /api/missions` lists up to 500 persisted plans. Both require the bearer token and PostgreSQL. Database-backed operation has not been verified on this host.
- The dashboard labels the plan and execution state separately. Generated tasks require assignment and an eligible `RECEIVED` or `ASSIGNING` state before the separately started worker can claim them. The worker uses the model router and assigned verified read-only internal tools; it does not provide independent output verification or automatic recovery.
- Host CPU utilization is calculated from per-core CPU-time deltas (the first sample is intentionally unavailable), RAM usage uses OS totals, and storage usage reports the volume containing the server user's home directory. GPU and disk I/O telemetry remain unavailable without an authorized host monitor.
- API health indicates configuration, not a successful provider connection. A model must be configured and exercised separately. No provider credentials are included in this repository.
- Phase 02 acceptance is not complete. There is no multi-agent execution, durable checkpoint/recovery, task-execution approval workflow, isolated tool sandbox, or authenticated user/role sessions. A live worker smoke test exists but is skipped by default and has not run against a live database/provider on this host. The separate project-plan review only approves or rejects a draft; it does not authorize execution.
- A policy/runtime Phase 02 foundation is available in `src/architecture/phase02-runtime.ts` and `GET/POST /api/phase02`. It covers in-memory agent discovery, capability advertisement, authenticated message envelopes, sandbox limits, independent evaluation, knowledge ingestion/search, approval requests, idempotent event deduplication, and audit entries. These are not claims of operational container isolation, durable queues, PostgreSQL persistence, remote A2A/MCP transport, or production execution.
- The advanced Phase 02 foundation is available in `src/architecture/phase02-advanced.ts` and `GET/POST /api/phase02/advanced`. It includes short-lived scoped credentials, revocation/delegation, signed receipts, versioned action authorization, simulation records, benchmark history, replay lineage, release promotion/rollback, bounded scheduling, workspace scopes, and evidence-bound feedback. It is not a claim of connected SPIFFE, OPA/Cedar/Casbin, container twins, GPU workers, or tenant-database enforcement.
